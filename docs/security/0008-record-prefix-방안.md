# 등록 레코드 이름 설정화 — 방안

## 문제

Client는 인증서 CN(`SimpleName`)을 요청 `Name`으로 보내고, 서버는 `Name`이 DNS 영역(`AzureDns.DnsZoneName`)으로 끝나야 처리한다. 등록할 레코드 이름이 인증서 발급 내용에 묶여 있어, 같은 인증서로 원하는 이름을 등록하려면 인증서를 다시 발급해야 한다.

또한 서버는 요청 본문의 `Name`·`Id`만 보고 처리하며, TLS로 인증된 클라이언트 인증서와 대조하지 않는다. 지금도 수정된 클라이언트는 유효한 인증서만 있으면 영역 안의 아무 레코드나 갱신할 수 있다.

## 목표

- Client 설정에 레코드 이름 prefix를 추가한다. 예: `bizadm.biz` 영역에 `home.bizadm.biz`를 등록하려면 `home`.
- Client는 prefix만 보내고, 서버가 영역을 붙여 처리한다. Client는 영역을 알 필요가 없다.
- 서버는 **TLS로 인증된 클라이언트 인증서**를 기준으로, 그 클라이언트가 해당 prefix를 갱신할 권한이 있는지 확인한다. 요청 본문 값은 권한 판단에 쓰지 않는다.

## 대안 — 권한 제한 방식

| 안 | 방식 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 서버 허용 목록 | 서버 설정에 클라이언트 인증서 식별자(지문 등) → 허용 prefix 목록 | 명시적·예측 가능, 관리자가 통제 | 클라이언트 추가·인증서 갱신 때마다 서버 설정 수정·재기동 |
| B. 레코드 소유자 기록 | 최초 등록 시 레코드 메타데이터에 인증서 식별자 저장, 이후 같은 인증서만 갱신 | 서버 설정 관리 불필요 | 선점 방식(먼저 등록한 쪽이 소유), 만료 삭제 후 다른 클라이언트가 가져갈 수 있음, 인증서 갱신 시 소유권 이전 수단 필요 |
| C. 인증서 이름과 대조 | 인증서 CN/SAN에 prefix가 포함돼야 허용 | 추가 저장소 없음 | 이름이 다시 인증서 발급에 묶여 이번 목표와 충돌 |

## 채택 방안

**A. 서버 허용 목록** (사용자 결정).

흐름:

1. Client 설정의 prefix를 요청 `Name`으로 보낸다.
2. 서버는 TLS 연결의 클라이언트 인증서를 얻는다.
3. prefix가 DNS 레이블 규칙에 맞는지 확인한다.
4. 서버 설정의 허용 목록에서 그 인증서에 해당 prefix가 허용돼 있는지 확인한다. 없으면 거부 응답.
5. 허용되면 기존 A/AAAA 갱신 흐름으로 `<prefix>.<영역>` 레코드를 갱신한다.

## 비범위

- 여러 DNS 영역 지원
- A/AAAA 외 레코드 타입
- 인증서 발급·배포 자동화

## 리스크

- 프로토콜 의미 변경: `UpdateRequestProto.name`이 전체 이름에서 prefix로 바뀐다. 이전 Client(전체 이름 전송)와 호환되지 않으므로 서버·Client를 함께 배포해야 한다.
- prefix 검증 누락 시 `a.b` 같은 다단계 이름이나 `@`(영역 루트) 등 의도하지 않은 레코드가 갱신될 수 있다. DNS 레이블 규칙으로 검증해야 한다.
